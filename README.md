# What's that?

It's Linux subsystem and proot builder.
Builds a Termux-based subsystem and proot, both set up in `config.yaml`: its `packages` section (the rootfs, auto-updated) and its `proot` section (proot's versions). All the generated files are ready-to-paste into jniLibs in Android Studio app project.

Both are built for every ABI Google Play supports: `armeabi-v7a`, `arm64-v8a`, `x86` and `x86_64` (`config.yaml`'s `abis`, with what each build calls them and the runner building them). A part can be built for some of them only (its `abis`), when Termux has no build of its package for the others: `minecraft` (OpenJDK 25 and cloudflared, for the Minecraft server) isn't built for `x86`, which OpenJDK dropped. That ABI's build and its `libparts.json.so` leave it out, and so the app leaves out the tool.

## Rootfs

`.github/workflows/build.yml` runs once a month (1st), on every push to main (but of the docs alone) and on demand, one run at a time: it builds PRoot (`build-proot.yml`, a job of it) and the rootfs for every ABI and releases them together, PRoot and its loaders in each ABI's folder of `rootfs.tar.gz` next to the parts, so the app gets everything from one release. A release is only published when a part or PRoot changed, with the parts' versions, PRoot's and a changelog of the differences per part.

Each part has its own version (`rootfs/release.py`): a part keeps the previous release's archive, byte for byte, and its version as long as what goes into it is the same - its packages (its merged manifest), its `config.yaml` entry and script, and the settings and build scripts every part shares. It also keeps them when its files come out the same as there (their contents, links and modes, not their times; the core's own `etc/image-version` aside), e.g. after a build script changed in a way that didn't touch it. Packed differently (`rootfs/pack.sh`: xz with the ABI's branch-call filter), a part with the same files gets the new archive but keeps its version, so the app has nothing to unpack again. So the app (and Play, for an extension's module) only updates the parts that changed. The release's `parts.json` has each part's version and, per ABI, its size unpacked, its archive's size and what it holds. The app gets each ABI's alone, without the hashes: `<abi>/libparts.json.so` in `rootfs.tar.gz`, next to that ABI's archives (a native library, so Play ships a device only its own).

The rootfs comes in parts (`config.yaml`): the core (`libpackage-core.tar.xz.so`: dash and what several parts link), which the app installs as an on-demand Play module (`core`, with PRoot) along with the first tool on Linux, and unpacks before it, and an extension per package (`libpackage-<name>.tar.xz.so`, e.g. `ytdlp`, which requires `python` and `ffmpeg`), which the app installs (as an on-demand Play module, with the tool's pages) and unpacks on a tool's first use, and deletes with its data. An extension holds its packages with their dependencies, minus what the parts it builds on have (`requires`: the core, or parts building on it); what two parts both need goes to the one they both build on (`rootfs/parts.py`). Each extension lists its files in `etc/extensions/<name>.files`, for the app to delete it again.

The rootfs is built from [Termux packages](https://github.com/termux/termux-packages) inside [termux-docker](https://github.com/termux/termux-docker) (`rootfs/build.sh`): the packages from `config.yaml` are installed, pip packages are installed (and built, with `build_packages`, against a part's `pip_libs`, e.g. pypkgs' Pillow against libjpeg-turbo and zlib), and only the files of those packages, their dependencies and what pip added are exported - not the rest of the Termux bootstrap, nor the build packages (`build_packages`: `python-pip`, the compilers), even when a package depends on them. Of the dependencies, only what a part's own packages use goes into it (`rootfs/parts.py linked`): the libraries they link (`DT_NEEDED`, all the way down), the interpreters their scripts run, and the data and modules of what's used; a part's own packages ship their programs and data, and their libraries when linked. So a part says only what it is for, and where its dependencies go follows from the `requires` tree: Python and FFmpeg both link zlib and OpenSSL, so those go to the core. A package nothing of which ships (all its files pruned or unused) isn't listed in a part either. The app lists everything a part holds, each with its version (`components` in `parts.json`), its own packages first. Termux's packages depend on a lot only their tools or their building need: FFmpeg's pull in libtiff, X11, cairo and Python (GLib's and libplacebo's packages depend on it), none of which it links, and its codecs' command line tools (`vpxenc`, `rav1e`, `cwebp`, ...) aren't needed either. Files the app's features don't need at runtime (docs, headers, tests, dev tools, unused Perl and Python modules) are pruned as well (`PRUNE_PATTERNS` in `rootfs/build.sh`). FFmpeg is built with Termux's recipe (`rebuild` in `config.yaml`, `rootfs/termux-build.sh`: its source, patches and configure step), without the configure options for what the tools don't use (more AV1 encoders, Vulkan, JPEG XL, disc and network formats, ...): Termux's links every one of them, so it can't start without them. It's installed over Termux's package, and only what it links ships. `rootfs/termux-build.sh` builds a Termux package natively from its recipe in termux-packages (fetched as a sparse checkout), linked for 16 KB pages; its build tools come from the recipe (`TERMUX_PKG_BUILD_DEPENDS`) and from `build_packages` for what Termux's build host has (nasm), and never ship. A part can leave packages out (`exclude`, with what only they need, `rootfs/parts.py reachable`): FFmpeg leaves out Termux's Vulkan loader, so libplacebo gets Android's own `libvulkan.so` with the GPU's driver (and Mesa's software driver, ~178 MB with LLVM, which only that loader would load, goes too), and Fontconfig's DejaVu fonts: it finds Android's in `/system/fonts`, which the app binds into proot. yt-dlp is Termux's too (`yt-dlp`, provided by `python-yt-dlp`, as `pkg install yt-dlp` installs it; `build.sh` takes such a name as the package providing it). The Termux prefix is in `usr/` of the archive; the app binds it to `/data/data/com.termux/files/usr` (where Termux binaries expect it) inside proot. Package maintainer scripts are not run.

Termux binaries use Android's own libc (bionic) and are linked for 16 KB pages, so they run on Android 15+ devices and Android 17 emulators with 16 KB pages. The workflow checks every ELF of the 64-bit rootfs for that. What Termux still ships linked for 4 KB pages (packages built before it moved to 16 KB, e.g. `libwebp`) is rebuilt by `rootfs/rebuild-16k.sh` with Termux's own current recipe of its package (`rootfs/termux-build.sh`; the NDK's cpufeatures from the NDK version Termux builds with, as Termux's NDK packages have no `sources/`), linked for 16 KB pages. Nothing is pinned: once Termux rebuilds a package, its files are aligned and are left as they are.

## PRoot

`proot/build.sh` cross-compiles [termux/proot](https://github.com/termux/proot) with a statically linked talloc. The loaders (`libproot-loader.so`, `libproot-loader32.so` on 64-bit ABIs) are built from the same source, so they always match the proot binary. It's built with every release (`build-proot.yml`, called by `build.yml`; run by hand, it only builds), and ships with the core (the app's rootfs module).

Patches in `proot/patches/`:
- `proot-loader-path.patch` - loader names are configurable and a relative loader path is resolved next to the proot binary (the app's `nativeLibraryDir`)
- `proot-tmpdir.patch` - fall back to `$TMPDIR` when `PROOT_TMP_DIR` is unset
- `proot-ashmem-include-string.patch` - missing `<string.h>` include (same as Termux)
- `proot-loader-16k-pages.patch` - loaders are linked for 16 KB pages too (they don't get `LDFLAGS`; the NDK only defaults to it for 64-bit ABIs)

`ref` and `talloc` in `config.yaml`'s `proot` section are `latest`: each build takes PRoot's newest tag and talloc's newest release (a fixed ref or version pins it; `NDK_VERSION` is in `build-proot.yml`). A patch that no longer applies fails the build.

## Releases

Releases are in the releases tab, with tags `YY.MM.DD`, each with the rootfs and PRoot. A rootfs part's version is the tag of the release it last changed in.
